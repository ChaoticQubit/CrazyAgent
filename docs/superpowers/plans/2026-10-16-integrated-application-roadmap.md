## Capacity supports a coherent alpha and conditional breadth

Assume one full-time owner with AI coding agents, **30-40 hours per week**, macOS first, Claude Code and Codex first. October 16-November 30 contains 32 weekdays: **192-256 gross hours**, approximately **154-205 feature hours after a 20% reserve**. The reserve covers real checks, required reviews, fixes, packaging, documentation and release qualification. At 35 hours weekly the totals are 224 gross, approximately 179 feature and 45 reserve hours. Holidays or time off reduce these numbers. Parallel agents do not multiply owner review and integration capacity.

The first month ends November 15: 21 weekdays, 126-168 gross hours, approximately 101-134 feature hours. November 16-30 adds eleven weekdays and approximately 53-70 feature hours. Dates below are planning targets, conditional on measured effort and qualification. Reforecast weekly rather than spending the reserve to preserve a feature count.

Reuse one qualified full application spine. Compare Omnigent's runtime/policy system with Emdash's local desktop foundation on pinned revisions, source build, native hosting, licensing, installation footprint and the complete project journey. Do not assume a fork is ready because it launches, or combine several full applications. Qualify auth separately: native Claude hosting and Codex app-server are candidates; SDK availability does not grant subscription-token permissions. ([Omnigent](https://github.com/omnigent-ai/omnigent), [Emdash](https://github.com/generalaction/emdash), [Codex app-server](https://developers.openai.com/codex/app-server/), [Claude legal](https://code.claude.com/docs/en/legal-and-compliance))

## The first five execution tasks qualify the critical path

These tasks start only after the proposed design is accepted and the applicable implementation workflow is completed. They produce runnable parts of the integrated app rather than throwaway standalone tools.

1. **Qualify one application foundation, 4 hours.** Compare pinned Emdash/Omnigent paths and select one. Acceptance: source/dependency/license inventory, a runnable project surface, native process hosting and a realistic path to protected verification. No install or redistribution assumption counts as proof.
2. **Qualify native sessions and profiles, 5 hours.** Run supported Claude/Codex modes in the project surface with native permissions and authentication. Acceptance: explicit account/billing mode, restart/recovery behavior, supported profile handles, independent logout/refresh and no consumer-token interception. Concurrent multi-account support remains conditional until tested.
3. **Qualify shared state and effective configuration, 4 hours.** Both harnesses consume the same project fact plus one supported skill/MCP definition. Acceptance: visible global/project precedence, predictable update/conflict behavior, unsupported fields shown, existing provider files preserved and no cross-project memory leak.
4. **Qualify peer communication, 3 hours.** A real Claude session sends a message Codex reads and vice versa. Acceptance: sender/project scope enforced, cross-project/forged-sender requests fail, bounds hold, reconnect does not repeat an action, and messages cannot edit protected authority.
5. **Qualify protected verification, 6 hours.** Execute a real pilot suite from an immutable candidate under an approved baseline. Acceptance: broken code plus always-pass tests fails protected behavior checks; coders/tests cannot edit policy or accepted evidence; forged results fail; later source edits make green evidence stale. If this boundary fails, change the foundation or date.

The order is dependency-aware; the 22-hour total is a timebox, not evidence already obtained. Dynamic spawning, adaptive task routing, swarms and automatic multi-stage workflows remain outside this proposal until their tradeoffs receive explicit approval.

## Verification authority is present from v1

Owner-approved checks, baseline and policy live outside coder-writable state. Coding processes, plugins, tools and candidate test execution cannot modify the controller or accepted result store. A disposable worker runs the immutable candidate without host credentials, Docker socket, unrelated projects or shared writable caches. The trusted controller records source, policy, baseline, environment/tool identities and actual execution evidence; any change makes earlier results stale. A separate AI reviewer or process is insufficient. Existing sandbox and integrity components are candidates to qualify, not proof of enforcement. ([Docker Sandboxes architecture](https://docs.docker.com/ai/sandboxes/architecture/), [Gauntlet](https://github.com/matthewjones372/gauntlet), [SLSA requirements](https://slsa.dev/spec/v1.2/build-requirements))

Use TDD for non-trivial implementation. Test real modules first; integration, whole-flow E2E and smoke checks use real systems. Each release checks the full create-project-to-evidence journey, recovery, account isolation and failure states. Unit/integration/E2E/smoke labels describe distinct evidence. Add a running-instance, medium/high/critical-gated nuclei check in PR CI when the application surface supports it, with unsupported local-only scope explicit.

Before push or PR, freeze one target and run the required code-review and Codex Security tracks in parallel. Preserve historical DeepSec findings/candidates and manifest, refresh deterministic candidates, and supply all evidence to the prescribed Daybreak/ChatGPT-auth security scan. No extra DeepSec AI pass. Resolve security/data-loss defects and critical/high findings; one confirmation round at most after substantial fixes. Missing review/model/auth/evidence setup is a real release dependency, not a clean result. Update the graph after code changes and again after review. Native auth, signing/distribution prerequisites and review setup must be qualified early without unapproved installations.

## November expansion requires evidence from actual use

Run the experiment from October 30 to November 13, or shift both dates if alpha slips. The following are proposed practical thresholds, not statistical market validation.

1. **Ten real tasks:** use the application for at least ten non-demo project changes, including both-harness and independent-verification workflows. Include at least two external users if available; otherwise retain external demand as an explicit gap.
2. **Material coordination benefit:** target at least 25% less manual coordination time or comparably fewer coordination actions than the owner's existing setup, with no worse valid-completion/defect outcome. Include one serious integrated competitor comparison where access permits.
3. **Daily reliability:** at least eight of ten supported workflows finish without outside context/configuration repair. Zero lost work, wrong-account inference, cross-project memory leaks or unauthorized verifier changes are acceptable.
4. **Honest verification:** every supported negative control fails for its intended reason, including broken behavior, always-pass tests, policy edits and forged/stale evidence. Unsupported or blocked checks stay visibly unverified.
5. **Preference after repetition:** the owner chooses the app for at least seven of ten working days. External feedback, if obtained, identifies a concrete integration advantage rather than liking the concept.

Continue breadth when the integrated workflow is preferred and the trust boundary holds. Rework integration when users want it but leave the app to coordinate core work. Stop broad expansion when there is no material benefit, the boundary remains unqualified, or a small extension of an existing app provides the same result. Upstream contribution is a successful alternative to maintaining a redundant fork.

If work runs late, cut third-harness breadth, native picker, deep analytics, automatic routing and remote sync first. Reduce supported languages before weakening verification. Move dates before consuming the reserve or dropping reviews. Preserve shared project state, direct communication, account separation and independent authority in the integrated release.
