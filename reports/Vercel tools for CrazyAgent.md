# Vercel tools for CrazyAgent

**Evaluate fx against RCLI before selecting a different harness; keep Vercel Sandbox an optional cloud execution backend.** Together they offer useful reasoning, protocol and isolation components, but they do not replace CrazyAgent's Rust policy engine, independent verifier, native worker supervision or independently complete TUI and Tauri desktop clients. fx is an experimental Apache-2.0 Zig coding agent with headless, ACP and JavaScript embedding surfaces. Vercel Sandbox supplies managed Linux Firecracker microVMs, with cloud authentication, billing and persistence obligations. Their combination is an integration proposal, not an already qualified CrazyAgent runtime or a demonstrated built-in fx capability. Preserve the accepted architecture and use the findings below to define a bounded future comparison. ([fx source](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/README.md), [Sandbox overview](https://vercel.com/docs/sandbox), [adopted architecture](../docs/superpowers/specs/2026-10-17-crazyagent-architecture-design.md))

Research date: October 17, 2026. This report synthesizes the completed [fx notes](../research_notes/Vercel%20tools%20for%20CrazyAgent/fx.md), [Sandbox notes](../research_notes/Vercel%20tools%20for%20CrazyAgent/sandbox.md) and [podcast notes](../research_notes/Vercel%20tools%20for%20CrazyAgent/podcast.md). The earlier [RCLI assessment](RCLI%20leader%20reuse%20assessment.md) and [dual interface assessment](Rust%20dual%20interface%20architecture.md) supply background, not current comparative benchmarks. Public documentation, source and the episode captions were examined. No product installation, account connection, provider execution, paid provisioning, runtime benchmark or security audit qualified either tool. Recommendations are proposals and do not change accepted decisions; implementation-phase code and security reviews remain deferred under project authority.

## fx offers stronger integration surfaces than a terminal transcript

**fx is a native Zig coding agent, not an in-memory shell.** Its inspected local executor runs real filesystem operations and native shell commands. The repository declares Apache-2.0, allowing reuse subject to its license and third-party notices. Its native CLI and embeddable SDK make it a serious candidate for the leader reasoning role or selected coding workers. Neither the source language nor a small binary establishes lower end-to-end latency, better reasoning or reduced total cost; those require measurements against the same tasks and acceptance contract. ([License](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/LICENSE), [local executor](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/core/execution/local_executor.zig#L58-L79), [SDK](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md))

Version boundaries matter. The inspected main revision was **c7f5a38af216f4bfd5a010ad3ab77059d095829e**, committed October 17. The latest published CLI release observed was **v0.0.14**, published October 16 and pointing to **1a070af32cdfaf8cd0da6de3dc7f053302828b17**. Main-branch behavior below is not automatically release behavior. The SDK also documents an API migration in 0.0.13, reinforcing the need to select and test one exact artifact. Published v0.0.14 assets cover macOS and Linux on aarch64 and x86_64; no Windows release artifact was observed. The README explicitly labels fx experimental. ([Main revision](https://github.com/vercel-labs/fx/commit/c7f5a38af216f4bfd5a010ad3ab77059d095829e), [release and assets](https://github.com/vercel-labs/fx/releases/tag/v0.0.14), [SDK migration](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#upgrading))

The most useful reuse choices are distinct:

| Component | What the evidence supports | CrazyAgent verdict |
|---|---|---|
| fx CLI and ACP | Headless requests, saved sessions and structured streamed control over a managed process. | Strong candidate for a bounded comparison with the accepted RCLI harness. |
| fx JavaScript SDK | Reusable agent/engine APIs, custom tools, host-provided credentials and durable-step primitives. | Consider when host-controlled tools outweigh an additional JS runtime and bridge. |
| fx terminal UI | A native terminal interface and browser terminal embedding surface. | Reuse selectively; neither supplies both complete CrazyAgent clients. |
| Vercel Sandbox | Managed Linux microVMs, command control, network policy and saved filesystems. | Optional remote execution backend for approved workloads. |
| Rust engine and local runtime | Existing authority for routing, admission, ownership, verification and memory approvals. | Retain; qualify each native and remote capability separately. |

The table's fx capabilities come from the [pinned README](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/README.md), [ACP manual](https://fx.sh/docs/using-fx/acp) and [SDK manual](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md); the Sandbox capabilities come from its [overview](https://vercel.com/docs/sandbox). The verdicts are this report's engineering recommendations under the [CrazyAgent contract](../docs/superpowers/specs/2026-10-17-crazyagent-architecture-design.md).

For a Rust application, **ACP is the clearest first comparison surface**. It uses newline-delimited JSON-RPC 2.0 over stdio, supports streamed messages and tool updates, and includes session loading, continuation, cancellation and permission requests. The documented connection handles one active session and prompt, so concurrent workers require separately supervised processes or connections. `fx ask` is smaller for batch jobs, with final stdout and diagnostic stderr, but final JSON alone does not provide the full supervision protocol. Rust can bridge ACP without introducing Node into this path. ([ACP manual](https://fx.sh/docs/using-fx/acp), [dispatch registry](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/acp/server.zig#L90-L110), [headless interface](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/README.md#for-coding-agents))

The SDK trades simpler host-tool customization for another runtime boundary. It exposes JavaScript APIs, not an established stable Rust embedding ABI. A JS sidecar can offer a narrower tool set whose execution remains Rust-owned; that exact restriction must be demonstrated before relying on it. Browser/WASM support does not prove compatibility with every Tauri webview, while the SDK's native backend has explicit platform requirements. Its browser terminal is not a Ratatui component. Consequently, a desktop-only SDK integration would leave TUI parity and shared policy work unfinished. ([SDK tool API](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#tools), [runtime matrix](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#runtimes-and-backends), [browser terminal](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#the-fx-terminal-in-a-browser))

The earlier RCLI assessment identified a TypeScript/Bun editable sidecar, without an established stable embedding SDK, at its October 16 source snapshot. That makes fx's explicit ACP and SDK interfaces a meaningful reason to compare integration cost. It does not prove fx beats the already selected harness or justify a new port. No fresh RCLI runtime comparison occurred here. The decision should turn on accepted outcomes, control completeness, provider/account compatibility, recovery and maintenance effort, rather than Zig versus TypeScript alone. ([Dated RCLI source](https://github.com/Backboard-io/Backboard-R-CLI/blob/51bee17e02344de5fffd89523ce2b73d5042f216/package.json), [earlier assessment](RCLI%20leader%20reuse%20assessment.md))

## Permission prompts and saved sessions do not establish containment

**The inspected native fx path runs with its host process's OS authority.** Command construction uses supplied or inherited process environment; exported parent secrets therefore belong inside the exposure model. The source search did not identify built-in Vercel Sandbox provisioning or native isolation using the inspected macOS/Linux sandbox mechanisms. This is bounded negative evidence from the pinned revision, not a universal audit conclusion. Running fx inside a separately configured sandbox is possible in principle; assuming fx creates that boundary is unsupported. ([Command execution and environment](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/core/execution/command_runner.zig#L1277-L1294), [macOS environment inheritance](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/core/shared/darwin_process_spawn.zig#L71-L76), [pinned source](https://github.com/vercel-labs/fx/tree/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src))

Current `auto` permission mode directly permits ordinary project edits and recognized development commands, including dependency installation, builds and tests; other actions can reach a model reviewer. `full-access` disables fx permission checks. Even a stricter mode is not evidence that every read and execution is admitted through CrazyAgent's policy authority. Preserve Rust admission before execution, restrict credentials and inherited environment, and test the actual filesystem, network and descendant-process boundaries. These are future integration requirements, not controls proven by this research. ([Permissions manual](https://fx.sh/docs/configure-fx/permissions), [permission fallback](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/core/permissions/permission_gate.zig#L77-L120))

Durability has several different meanings. ACP can reload or continue saved conversations, but server shutdown cancels the connection loop; this does not establish that a live native worker survives leader or UI loss. The SDK records durable steps and documents stable execution IDs and replay rules, while interrupted non-idempotent tools can already have produced effects. Node session storage can default to a temporary directory unless configured deliberately. None of this establishes universal exactly-once external actions. CrazyAgent still needs explicit ownership, reattachment, interruption reconciliation and durable storage semantics. ([ACP lifecycle implementation](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/src/acp/server.zig#L979-L991), [SDK durability](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#durability), [tool replay contract](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/sdk/README.md#L185-L225))

Reuse the harness interfaces, context-loading conventions and explicit recovery primitives where they fit. Do not delegate immutable verification, approved memory promotion, worker ownership or project admission to a conversation-level permission setting. `AGENTS.md`, skills and saved chat histories are useful context mechanisms; the inspected documentation did not establish an equivalent to CrazyAgent's human-approved project-to-global memory promotion or protected verifier contract. ([fx instructions and sessions](https://github.com/vercel-labs/fx/blob/c7f5a38af216f4bfd5a010ad3ab77059d095829e/README.md), [CrazyAgent authority](../docs/agent-decisions.md))

## Sandbox buys Linux isolation and capacity with cloud obligations

Vercel documents **a Firecracker microVM per sandbox**, command execution with streams and signals, interactive CLI PTYs, declared development-server ports and network controls. This is useful for untrusted dependency/build workloads and machines short of CPU or memory. Its Linux environment is not a macOS or Windows native desktop qualification environment. Public development URLs are exposure surfaces, and copying files or cloning a repository is not a transparent mount of CrazyAgent's local Git worktree. Rust must own the source revision, artifact transfer and acceptance contract. ([Overview](https://vercel.com/docs/sandbox), [SDK commands](https://vercel.com/docs/sandbox/sdk-reference), [CLI and PTY](https://vercel.com/docs/sandbox/cli-reference))

Official JS/TS and Python SDKs, CLI and REST interfaces offer several integration paths. No official Rust SDK or complete self-hosted managed Sandbox service was identified in the reviewed interfaces. A Rust HTTP adapter avoids a mandatory JS runtime, but reconnects, streaming, interactive input, signals, cancellation and retries require qualification. A JS SDK sidecar reduces custom protocol work while adding packaging and supervision costs. CLI PTY support was documented; equivalent interactive control entirely through the REST surface was not established. Vercel infrastructure authentication, through project OIDC or an access token, is separate from the agent's model subscription or API account. ([Published integrations](https://vercel.com/docs/sandbox), [REST API](https://vercel.com/docs/rest-api), [authentication](https://vercel.com/docs/sandbox/concepts/authentication), [public client repository](https://github.com/vercel/sandbox))

Network policy supports unrestricted, blocked and custom egress. Header brokering can keep a provider secret outside the VM, but delegates handling to Vercel. Domain allowances still permit data to leave through allowed destinations; ordinary TLS forwarding is not full HTTP inspection. Header rewriting requires TLS termination and a sandbox CA. These controls need a deliberately chosen Rust-owned policy and compatible client configuration. Separate Linux users inside one VM are also a weaker separation than distinct microVMs; a verifier sharing a guest with a root-capable worker is not automatically immutable. ([Firewall](https://vercel.com/docs/sandbox/concepts/firewall), [multi-agent users](https://vercel.com/docs/sandbox/concepts/multi-agent), [SDK execution](https://vercel.com/docs/sandbox/sdk-reference))

**Current persistence defaults change the disposable-worker assumption.** Stopping or timing out a persistent sandbox saves its filesystem; resuming boots a new session from those files. Tokens, agent histories and customer code written there can therefore remain after a worker stops. Snapshots can outlive a deleted sandbox and continue accruing storage charges; drives add another retention surface. Disposable tasks need deliberate non-persistent configuration and explicit snapshot/drive retention. Saved files do not imply a stopped process or PTY resumes alive. ([Persistent sandboxes](https://vercel.com/docs/sandbox/concepts/persistent-sandboxes), [snapshots](https://vercel.com/docs/sandbox/concepts/snapshots), [drives](https://vercel.com/docs/sandbox/concepts/drives))

For planning, use the dedicated pricing reference dated **September 10, 2026**. It bills active CPU at **$0.128 per CPU-hour** and allocated RAM at **$0.0212 per GB-hour** in the example region. CPU waiting on I/O is excluded from active CPU, while RAM remains billable. Ten Pro workers allocated 2 vCPU and 4 GB each for one hour produce this illustrative usage estimate, not an observed invoice. ([Pricing and quotas](https://vercel.com/docs/sandbox/pricing))

Local execution retains offline operation, native applications and local worktrees without cloud upload or resource charges. It also requires qualified local confinement and budgets. Anthropic's sandbox-runtime is an available source-level reference for macOS/Linux filesystem and network controls; it is not proof that CrazyAgent's aggregate CPU, RAM and process limits pass. A remote option is most valuable as additional capacity and a separate Linux boundary, with explicit data-transfer consent and bounded spending, while local native work remains independently supported. ([Local sandbox-runtime](https://github.com/anthropics/sandbox-runtime), [CrazyAgent implementation contract](../docs/superpowers/plans/2026-10-17-crazyagent-implementation-plan.md))

## A bounded comparison can answer the remaining decision

The decision-changing exercise is a future **pinned fx-versus-RCLI qualification under the same Rust-owned acceptance contract**. It should establish usable structured events, tool admission completeness, credential isolation, cancellation and descendant handling, leader/client-loss recovery, account compatibility and both-client observability on representative tasks. Measure accepted outcomes, wall time, resource use, token cost and adapter complexity. Choose ACP first unless its host-control boundary proves insufficient; compare the SDK only for a demonstrated gap. This is a proposed evaluation scope, not an approved implementation task or a claim of superiority.

Sandbox needs a separate acceptance decision covering provisioning, source/artifact integrity, network and secret policy, resource and spending limits, retention, cancellation, and the verifier's independence from worker authority. Linux VM success cannot qualify local native desktop behavior. An unavailable or untested capability stays unavailable rather than being silently replaced.

The useful architectural gain is **replaceable components with observable boundaries**. fx can compete for the reasoning harness, Sandbox can compete for remote execution, and the Rust engine can retain the policy and recovery contracts that make both clients one product. Keep the existing runtime direction until those comparisons produce evidence that justifies a change. No permanent runtime adoption is recommended by this research.
