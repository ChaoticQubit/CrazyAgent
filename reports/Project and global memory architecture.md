# Keep project memory useful and bounded

**The approved hierarchy captures activity once, curates project knowledge asynchronously, and promotes reusable knowledge through a separate global role.** This extends CrazyAgent's accepted Rust engine, primary TUI plus desktop interface, native Claude Code/Codex workers, and editable RCLI leader harness. It does not require another orchestration framework. The owner described the hierarchy in [DEC-020](../docs/agent-decisions.md#dec-020-log-derived-project-and-global-memory-agents) and explicitly approved the architecture assessment and human review inbox in [DEC-021](../docs/agent-decisions.md#dec-021-approve-asynchronous-memory-architecture-and-human-review-inbox). [DEC-022](../docs/agent-decisions.md#dec-022-immediate-provisional-project-memory-and-approved-global-promotion) records Q-014 A: curated project knowledge is immediately retrievable as provisional; global promotion requires prior human approval. Detailed mechanisms below remain implementation proposals wherever the numbered register leaves them unresolved. Comprehensive recording means exposed, authorized activity with visible coverage limits, without a guarantee of access to every private reasoning token. Runtime behavior, capture completeness and performance remain to be qualified.

## Capture exposed events and show missing coverage

**Proposal:** Rust owns one structured activity stream. Provider adapters attach project, session, worker, parent-worker, source-event and ordering identifiers, plus model/adapter versions and completion status. Store chat, exposed thinking, tool inputs/results, command output, file activity, approvals, cancellation and usage where available. The UI should distinguish captured, summarized, redacted and unavailable content.

OpenAI private reasoning tokens are unavailable through the Responses API. Usage counts, readable summaries and opaque encrypted replay state are different artifacts. Codex app-server documents messages, command/output events, collaboration items and reasoning summaries; reasoning-text deltas depend on model support. This does not establish universal private-token access. ([OpenAI reasoning](https://developers.openai.com/api/docs/guides/reasoning), [Codex app-server](https://learn.chatgpt.com/docs/app-server))

Current Claude thinking documentation describes summarized or omitted thinking, rather than guaranteeing raw reasoning for every model. Its Agent SDK top-level incremental stream excludes sub-agent token deltas; complete messages provide parent attribution, while hooks expose separate sub-agent transcript paths. **Native adapters need qualification across versions, launch paths, children and reconnects.** API capabilities alone do not prove subscription-authenticated CLI coverage. ([Claude thinking](https://platform.claude.com/docs/en/build-with-claude/thinking), [SDK streaming](https://code.claude.com/docs/en/agent-sdk/streaming-output), [Claude Code hooks](https://code.claude.com/docs/en/hooks))

## Background jobs keep curation outside coding turns

**Proposal:** Each project's memory agent is a scheduled role, not a permanently running model. Turn completion, idle intervals and explicit requests enqueue durable jobs. Incremental cursors select only new events; stable candidate IDs make retries idempotent. Worker/user “remember this” submissions enter the same pipeline with priority and provenance. Hooks enqueue and return; the Rust dispatcher owns subsequent execution. Claude documents teardown constraints for asynchronous hooks, making hook-process survival an unsuitable durability guarantee. ([Hooks reference](https://code.claude.com/docs/en/hooks))

LangGraph documents background formation and namespace/key memory organization; reuse those ideas without integrating LangGraph. ([Memory overview](https://docs.langchain.com/oss/python/concepts/memory)) Bound batch size, concurrency, input/output tokens, retries and total project/global expenditure. Deduplicate before inference and avoid rereading complete histories. Separate capture from inference queues, expose backlog age and capture gaps, and define disk-pressure behavior. Background work still consumes resources; no latency or cost guarantee has been measured.

## Curated memory needs evidence and reversible versions

**Proposal:** Separate the event archive, candidate inbox, retrievable project memory and global nominations. A memory records its claim, scope, source-event references, relevant repository revision, author/curator, uncertainty, freshness and version. Deduplicate equivalent claims, preserve conflicting evidence, and supersede stale entries. Model reasoning is a source of hypotheses; tool results and verification artifacts substantiate factual claims.

The human inbox provides **keep, edit and remove** controls, source inspection and visible history. Corrections invalidate retrieval caches and derived memories, notify active workers, and mark dependent conclusions for reconsideration. Removal prevents future retrieval according to policy; it cannot erase context a running agent already consumed.

The owner selected **Q-014 A**, recorded in DEC-022: source-backed project memories become immediately retrievable with a provisional label and subsequent human controls, while global promotions require prior approval. The alternative requiring prior approval for every project update was not selected. Ordinary memory cannot change permissions, protected decisions or verification baselines; provisional findings cannot count as proof.

## Project boundaries must survive every promotion

**Proposal:** Enforce project isolation in the Rust storage and retrieval layer, including artifacts, queues, searches and exports. Curators receive only their project's authorized material. The global curator receives explicit nominations with minimal supporting excerpts, never default access to every project's logs. Generalize nominated knowledge and remove private code, paths, identifiers and secrets before cross-project publication. Global retrieval follows an explicit access policy.

Treat logs, tool output and worker submissions as untrusted data. Curation prompts must not turn embedded instructions into authority. Restrict curator tools, require source-backed claims and flag suspicious nominations. Human review complements these boundaries; it does not replace them.

Filter secrets before ordinary-log storage and again before distillation. Redaction is imperfect, so define encryption, access controls, retention, deletion/export behavior and whether protected original protocol artifacts are necessary. Never interpret encrypted reasoning blobs as text. Transactional local storage, with SQLite as a candidate, can hold metadata, job cursors and versions; large outputs can remain referenced artifacts. SQLite WAL supports concurrent readers and one writer, with local-host and checkpoint constraints. It needs workload validation, and a semantic database is not yet justified. ([SQLite WAL](https://sqlite.org/wal.html))

## Conclusion

The useful distinction is between recording evidence and granting knowledge authority. A project curator can operate promptly without becoming a privileged policy engine, and a global curator can share lessons without acquiring every project's history. The architecture and Q-014 activation policy are approved. [DEC-023](../docs/agent-decisions.md#dec-023-approved-cloud-or-local-destinations-for-memory-processing) records Q-015 A: curation can use cloud or local models within approved provider/account destinations and resource authority; an unapproved destination requires approval. [DEC-024](../docs/agent-decisions.md#dec-024-retain-captured-activity-until-explicit-deletion-by-default) records Q-016 A: retain captured activity until explicit deletion by default, with visible storage usage and optional configurable expiry. Storage-pressure behavior, capture coverage and bounded queue performance still need qualification. The numbered decision register tracks the remaining questions and supersedes older research recommendations when the owner selects a policy.
