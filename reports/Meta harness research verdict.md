# Build a Smaller, Honest CrazyAgent First

**Research: Good. Idea: Promising. Decision: Reshape and build a narrow experiment.** Do not abandon CrazyAgent's purpose: reducing the effort of operating several coding agents is a credible personal problem and a useful open-source goal. Do abandon the present promise that fifteen features, arbitrary harnesses, identical sessions, portable credentials, and surviving background work can arrive quickly in one universal platform. My recommendation is a small, opinionated integration for two harnesses, with explicit compatibility and recovery reporting, built around existing components. Its value would be fewer setup and recovery minutes, not a claim to invent the meta-harness category. A separate runtime earns consideration only after existing tools fail a repeatable comparison. This is a recommendation to validate the narrower project, not a claim that its feasibility or adoption has already been demonstrated.

Assessment date: **October 16, 2026**. The team read the complete supplied research, approximately 14,700 words, and checked material claims against primary documentation, papers, and repositories. This report separates documented capabilities, research observations, inference, and proposed ideas. It does **not** claim that all 308 bibliography links or every competitor-matrix cell were independently verified. No competitor was installed or exercised, and no users were interviewed.

## Your research finds real problems but does not validate the whole solution

Your idea is an operational layer above existing coding harnesses. You want to install once, use existing agents, move unfinished work between them, preserve useful context, manage isolated workspaces, and assess whether the resulting work deserves trust. Shared configuration, usage analysis, native UI feedback, automatic routing, and cross-machine availability extend that goal. The crucial distinction is that you explicitly want an **open-source project for practical use**, not necessarily a company. Commercial market size is therefore secondary to repeated usefulness and maintainable scope. ([Original research](../docs/Meta-Harness%20%E2%80%94%20Decisions%20Features%20%20Research%20Data.md))

The research is good because it records concrete owner problems, separates requirements from unresolved decisions, includes competing implementations, and preserves negative evidence and unverified claims. It also recognizes boundaries that undermine easy promises: hooks differ, session transfer is incomplete, runtime dependencies survive packaging, and routing can lose quality. This is substantially better than a feature wish list with a market-size paragraph attached.

It falls short of great research in **traceability and experimental validation**. Most citations live in the final bibliography rather than beside individual claims. The capability matrix merges “absent” with “not documented,” while a positive entry often means documented rather than tested. Complaint threads are selected samples; overlapping issues and reactions are not independent users. Benchmark failure rates, surveys, vendor announcements, and repository studies measure different populations. They cannot be added together to prove demand for one bundle.

The missing evidence is small but decisive: how often the owner's workflow fails, how much recovery costs, which existing tool already solves it, and whether one integrated setup improves the outcome. The document establishes an opportunity to investigate, not a validated architecture or a commitment to maintain fifteen features. The following corrections are the most consequential examples, rather than an exhaustive fact-check.

## Existing tools already challenge the integrated application thesis

The strongest competition is more serious than several small terminal managers. **Omnigent explicitly calls itself a meta-harness**, Traycer already integrates cross-provider history replay, and established IDE vendors host multiple agents. Your research recognizes much of this, but misses material release drift and additional direct competitors. The table describes primary-source capabilities, not independently qualified operation.

This does **not** make the project pointless. Integrated usability can be a legitimate open-source contribution even when every underlying component exists. A developer who spends an hour assembling five tools has a different problem from a maintainer who sees five capable repositories. Your strongest argument is that setup, defaults, and failure recovery remain fragmented. The counterargument is that another wrapper becomes another stateful dependency, and documentation alone cannot tell which argument wins.

Commercial evidence cannot decide that question. Bloop's shutdown statement says Vibe Kanban had thousands of daily engineers and failed to find a compelling business model; the project continued through open source/community maintenance. That warns about maintenance economics without proving that noncommercial tooling is unworthy. Stars, funding, and agent adoption show attention to the category, not prospective CrazyAgent retention or contributor capacity. ([Maintainer statement](https://www.vibekanban.com/blog/shutdown))

## Portability needs explicit losses and provider-specific boundaries

**A shared project is feasible; one identical execution everywhere is not established.** Five different things are being grouped under “continuity”: transferring information, importing configuration, resuming agent history, recreating an environment, and continuing running effects. A useful tool names those separately. Claude's session documentation, for example, describes persistent conversation state while excluding some live Bash/monitor state and requiring some launch configuration again. An outer launcher does not automatically acquire control over hidden child-agent state. ([Claude sessions](https://code.claude.com/docs/en/sessions))

The credible contract is a versioned package of decisions, repository identity and dirty work, relevant history, prerequisites, pending operations, and check evidence. The destination should report unsupported hooks, missing authentication, changed paths, and permissions requiring a new decision. A hash establishes artifact identity, not that a claim inside it is true. Imported memory needs provenance and conflict handling; two agents writing to one store do not automatically produce one trustworthy truth. These are engineering inferences from the documented protocol boundaries, not tested CrazyAgent behavior.

“Everything is sandboxed” also needs concrete meaning. Worktrees isolate source changes, not processes or networks. OS sandbox restrictions, tool permissions, repository instructions, and credentials are separate controls. An adapter that cannot preserve a required restriction must report failure instead of silently widening access. Portable file formats such as Agent Skills help distribution without guaranteeing identical dependencies or allowed-tool enforcement. ([Agent Skills specification](https://agentskills.io/specification), [Claude sandboxing](https://code.claude.com/docs/en/sandboxing))

Authentication is a material dependency, with a distinction your final design must preserve. OpenAI's **Sign in with ChatGPT integration terms** prohibit enabling account rotation or splitting to bypass usage limits. Those terms concern applications integrating SIWC; they do not establish that multiple legitimate subscriptions or every wrapper around the official CLI is forbidden. They also distinguish local, user-controlled persistent token storage from user-controlled remote requests. Do not build a central credential vault or quota-bypass feature on the assumption that remote execution permits either. ([SIWC terms](https://openai.com/policies/sign-in-with-chatgpt-terms/))

Anthropic similarly distinguishes prohibited collection/intermediation of consumer tokens from users signing into an unmodified hosted Claude Code binary, subject to stated conditions. Official-client use, API-key billing, third-party OAuth integration, and subscription-limit circumvention need separate treatment. The AUP text effective November 12, 2026 is future policy on this assessment date. These readings identify constraints; they do not constitute vendor authorization or settle every implementation's legal status. ([Claude legal guidance](https://code.claude.com/docs/en/legal-and-compliance), [Consumer Terms](https://www.anthropic.com/legal/consumer-terms), [future AUP](https://www.anthropic.com/legal/aup))

Finally, independent verification cannot generically certify that tests are correct. Protected runners address tampering; production-path execution addresses mocks and bypasses; mutation checks test sensitivity; behavioral acceptance requires a credible oracle. None substitutes for the others. ImpossibleBench demonstrates shortcut behavior under deliberately conflicting tasks, while Gauntlet's evaluation is author-reported and not a certification of arbitrary code. The useful promise is evidence of specific checked properties, with unknowns exposed. ([ImpossibleBench](https://arxiv.org/html/2510.20270), [Gauntlet](https://github.com/matthewjones372/gauntlet))

## Four creative directions improve outcomes without inventing false novelty

The following are **proposed combinations to test**, ranked by practical fit. They are not claims of unprecedented invention, and none was implemented during this review.

### 1. A compatibility doctor that tests the installed combination

A developer moves from Claude Code to Codex. Before work continues, CrazyAgent shows which instructions were discovered, which hooks were dropped, which permission rules retain their meaning, and which MCP connections need local login. Its distinctive artifact would be a public corpus of real interruption, denial, stale-evidence, and dirty-checkout cases against supported version pairs. Think of it as an executable compatibility statement instead of another table of checkmarks.

oneharness already maps capabilities and avoids unsafe permission translations; UseAgent already distinguishes contract testing from live provider parity. The opportunity is to catch consequential workflow failures or reduce setup effort beyond those baselines. If it cannot, contribute the missing cases upstream. ([oneharness](https://github.com/nickderobertis/oneharness), [UseAgent](https://useagent.org/docs/architecture/shared-packages/))

### 2. A recovery receipt centered on uncertain side effects

A session stops after editing files, while tests run and a migration might have reached its target. The successor needs to know what is complete, what failed, and what is unknown before replaying anything. A recovery receipt would bind those observations to the source revision and current environment. A branch-scoped conflict inbox could preserve two incompatible decisions until their sources are reconciled, instead of silently turning one into shared memory.

AET already supplies portable evidence, Handover offers continuity records, and provenance-linked portable memory has research prior art. The narrower question is whether presenting unfinished effects together saves recovery decisions. It does not imply generic exactly-once execution or transparent subprocess revival. ([AET](https://github.com/AdvancingTitans/agent-engineering-toolkit), [Handover](https://handover.sh/guides), [Portable Agent Memory](https://arxiv.org/abs/2605.11032))

### 3. A verification policy that survives changing harnesses

Claude implements a change and Codex continues it. One independent acceptance receipt should show whether checks match the current source, whether relevant tests can fail, and whether verification machinery changed. The useful application is carrying a protected verification policy across the handoff, with an understandable owner decision when evidence becomes invalid.

Gauntlet directly overlaps this idea through base-controlled checking, fresh-process evidence, mutation testing, scenario bindings, and holdouts. Its current scope is broader than the source document's snapshot. A cross-host adapter or evidence consumer is the stronger contribution hypothesis. More generated tests or a second model's approval would not supply the same assurance. ([Gauntlet](https://github.com/matthewjones372/gauntlet))

### 4. A native UI failure packet that preserves the user's journey

A Mac dialog clips a button only after resizing and opening a menu. The user marks the button once; a packet preserves build identity, screenshot, window geometry, available accessibility data, and the action sequence. A later run repeats the journey and records before/after evidence. This goes beyond an annotated image by preserving the conditions needed to evaluate the fix.

Your research already identifies native capture tools, and Peekaboo documents screenshot/accessibility functionality. Apple sandbox and Electron accessibility constraints mean arbitrary-app element inspection and source-file mapping cannot be promised. The specific before/after composition remains an unvalidated opportunity, not a discovered empty market. Keep it separate until the continuity workflow proves useful. ([Peekaboo](https://github.com/steipete/Peekaboo), [Apple DTS](https://developer.apple.com/forums/thread/756130), [Electron](https://www.electronjs.org/docs/latest/tutorial/accessibility))

## A two-week comparison should decide whether CrazyAgent deserves expansion

My preferred project shape is **a thin, opinionated distribution with a reusable compatibility corpus**. Start with the owner's two principal harnesses and one operating system. Preserve native login and native runtime behavior, reuse an existing workspace host, and integrate verification/evidence components where their licenses and interfaces permit. A new GUI, cloud account, credential service, sandbox engine, and universal memory database each create maintenance obligations before the core benefit is measured. This is a proposed boundary, not an implementation authorization or completed design.

Contribute-first alone is insufficient if it leaves the owner assembling a pile of tools. Conversely, integration alone does not justify reimplementing sound components. A small distribution can own installation, tested combinations, intelligible failures, and support documentation while sending general fixes upstream. Use existing trajectory formats such as Harbor ATIF when they fit, rather than making another transcript format the project's identity. Redistribution rights and compatibility still require assessment before bundling. ([Harbor ATIF](https://docs.harborframework.com/agents/atif))

The smallest informative comparison uses actual interrupted work, native resume/import plus ordinary handoff notes, the closest existing host, and the proposed integration. Keep repository states and acceptance conditions comparable; measure valid completion as well as recovery time. Use synthetic external effects for interruption tests. Include a missing hook, denied permission, dirty worktree, stale result, and uncertain operation. Do not award success because a session merely opens or prints green output.

| Decision checkpoint | Proposed rule, not a measured result |
|---|---|
| Establish recurring pain | Record ten real interruptions or switches. If this is rare and consumes under roughly thirty minutes weekly, a recipe is probably enough. |
| Test existing solutions first | If an existing setup handles at least nine of ten cases acceptably, contribute the remaining case or publish the integration recipe. |
| Demonstrate practical improvement | Across forty observed recoveries, target a 50% median recovery-time reduction with no observed lost work, silently widened authority, or unauthorized replay. Zero observed incidents does not prove safety. |
| Check external usefulness | If ten suitable users participate, target eight completing setup within ten minutes and six returning for at least three real sessions over two weeks. These are suggested thresholds, not statistically validated adoption estimates. |
| Bound maintenance | Set an explicit budget, initially around two hours weekly for the supported pair. Repeated excess or dependence on unstable private transcript parsing should trigger narrowing, upstream contribution, or stopping. |

No large recruitment exercise is required before a personal tool can be useful. If external participants are unavailable, run the owner's comparison and call the result a personal-workflow result. Do not promote it into general demand evidence. The first adoption signal is somebody choosing to use it again after a real failure, not a star or a favorable comment.

**Build the narrow integration; abandon the universal release promise.** Stop the independent project if existing tools already remove the pain, meaningful improvements depend on unacceptable provider constraints, or adapter maintenance consistently exceeds the saved effort. Expand only when a concrete recovery benefit survives those comparisons. CrazyAgent's strongest identity is helping a person understand and preserve unfinished work across tools, with explicit limits. That can deserve an open-source project even in a crowded category.

Immediate next action: write down the last Claude-to-Codex interruption that cost you recovery time, including the first thing you had to reconstruct. That single case is a better starting point than choosing another feature.
