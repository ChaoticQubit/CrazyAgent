# Integrated CrazyAgent application: delivery feasibility and release design

## Can one integrated application be delivered quickly without turning into another tool recipe?

### Takeaway

The corrected product is worth a bounded build experiment: one installed, project-centric application that coordinates native harnesses, shared project state, communication, accounts, and independent evidence about their work. A public integrated alpha on October 30 is a conditional engineering target, not an evidence-backed promise; qualifying the native-hosting and verifier boundaries by October 21-22 is its critical dependency.

### Cited Findings

- The owner explicitly requires integration, not a company, and the original feature list includes fifteen areas with demanding semantics such as automatic subscription switching, preservation of subagents and background work at limits, and sessions/accounts following the user to another machine. The latest decision record supersedes the standalone workflow milestone proposal and requires a create-project, launch-harnesses, share-context, communicate, verify-work flow in the first release. The owner now explicitly requires verification of both code and the integrity of agent-written tests with trusted rules protected from the coding harnesses. [Original requirements](../../docs/Meta-Harness%20%E2%80%94%20Decisions%20Features%20%20Research%20Data.md), [current decisions](../../docs/agent-decisions.md).
- Codex app-server is an official integration surface for rich clients and explicitly covers authentication, conversation history, approvals, and streamed events. Its availability supports evaluating a real product integration rather than assuming terminal-output scraping is the only path. This says nothing by itself about permitted multi-account usage or bypassing plan limits. [Official app-server documentation](https://developers.openai.com/codex/app-server/).
- Claude Agent SDK provides the agent loop and context management that power Claude Code; its overview describes a library running the Claude Code binary with built-in tools, permissions, sessions, and hooks. That technical reuse does not establish permission for a third-party application's consumer subscription authentication or billing model. The native unmodified interactive CLI remains the initial hosting candidate pending the separate authentication qualification. [Official SDK overview](https://platform.claude.com/docs/en/agent-sdk/overview).
- ACP provides editor-to-agent session setup and optional MCP connections. Its session loading replays the agent's own retained history; this is not proof of portable native runtime state or universal plugin semantics. [Protocol source](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/session-setup.mdx).
- Tauri capabilities control the WebView-to-core boundary, while the Rust application core and plugins have full system resource access. A separate pane, Rust process, or capability manifest is therefore insufficient evidence that coding harnesses cannot modify verifier policy or forge its evidence. [Tauri security model](https://v2.tauri.app/security/).
- Existing reuse candidates already span desktop orchestration and isolation. Omnigent documents a common layer over native harnesses and terminal/browser/desktop surfaces, while Docker Sandboxes documents agent-specific microVMs and separate isolation layers. These are qualification candidates, not a decision to redistribute them or an assumption they fit the required user experience, authentication, installation, licensing, or performance constraints. [Omnigent official repository](https://github.com/omnigent-ai/omnigent), [Docker Sandbox isolation](https://docs.docker.com/ai/sandboxes/security/isolation/).
- Docker read-only bind mounts restrict writes to the mounted host data, with documented caveats for recursively mounted submounts. A verifier design must qualify the exact mount and runtime behavior it actually uses rather than inferring protection from a directory convention. [Docker bind mount documentation](https://docs.docker.com/engine/storage/bind-mounts/).

### Inferences

The product should have one project model from the beginning. Its minimal interface needs a project list, a project workspace with native harness sessions, shared context/configuration, a communication inbox, and verification results tied to specific changes. These can be tabs or panels within one window. The product milestone is completing work through those connected surfaces, not checking that five disconnected integrations individually launch.

The first technical qualification should compare extending an existing host with building a minimal shell around permitted native integration surfaces. Use the architecture lane's approximately 22 implementation-hour qualification budget, spanning October 16-21 at the upper capacity or October 16-22 at 30 hours weekly while retaining the reserve. Prefer the path that can demonstrate the full workflow and enforce the trust boundary with the least custom lifecycle code. Existing UI code is useful only if it permits the corrected application model and does not force unsafe account, permission, or verification behavior.

The trusted verifier must be designed as an application capability with an enforceable boundary. The initial design should include all of the following:

1. Owner-approved verification policy and trusted checks live outside the agent-writable project and shared memory. Whole-process restrictions cover each coding harness, its subprocesses, configured tools, and any path by which it could ask a trusted broker to write those files. A separate process under an otherwise unrestricted user is insufficient.
2. The trusted controller obtains an immutable source snapshot and records its digest, policy version, check versions, and relevant dependency/environment identity. Project test code runs as untrusted input, without write access to the controller, policy, or trusted evidence store. Its stdout is not itself authority to mark a change verified.
3. The first alpha contains a real negative control: an intentionally broken implementation paired with agent-visible always-pass tests must fail an independently protected behavioral check. Attempts to edit the policy, overwrite a result, or reuse green results after a source change must also fail. This demonstrates the supported boundary; it does not prove that all cheating or incorrect tests are detectable.
4. The UI shows verified, failed, stale, and unsupported separately. Coding agents can propose new checks or policy changes, but only an owner-authorized action can update the trusted policy. A change in code or policy invalidates older green evidence.
5. Verification covers the project code and signals about its tests. Initial signals can include protected behavior checks, changed-test execution against a known-bad revision, and test/config weakening detection. Broader mutation testing, held-out scenarios, and additional language integrations expand later. They do not replace the first release's real integrity check.

Those boundaries are a design proposal, not a security qualification already performed. Host services, native tooling, OAuth refresh, profile paths, network access, and application IPC must be included in the qualification. No launch should weaken native permissions, silently switch to API billing, or treat a copied policy file as independent enforcement.

Three integrated product ideas are more defensible than another generic agent chat surface:

1. A project evidence board connects a requested outcome, responsible sessions, actual source revision, protected checks, and current result. When an agent says a feature is done, the app shows exactly which claims have fresh evidence and which are still claims.
2. Shared context has provenance and scope. Owner decisions, agent observations, and verifier outcomes remain distinguishable; global preferences can be inherited by a project without silently promoting one agent's speculation into a global fact. Start with versioned plain records, not a new semantic-memory platform.
3. Configuration has a compatibility preview inside the app. A skill, rule, plugin, MCP server, or setting shows where it applies, which global/project value wins, and which behavior has no equivalent in the other harness. The app earns trust by making the common configuration usable and the exceptions visible.

Practical first workflow: create a project in CrazyAgent; assign a feature to Claude and a bounded review task to Codex in separate worktrees; both read the same project decision and supported skills; Codex sends a project-scoped question through the application; the owner sees the answer and resulting change; the independent verifier rejects an always-pass test on a broken implementation and accepts the corrected implementation under the frozen policy; reopening CrazyAgent restores project records and session links. Everything necessary for the supported workflow occurs within the application.

### Gaps

- No implementation, component reuse, redistribution rights, installation path, signing identity, live account compatibility, or live isolation boundary was qualified in this research lane. A framework or repository being available is not a delivery estimate.
- Shared plugins/settings have incompatible semantics. A compatibility catalog and supported subset are feasible; universal equivalence cannot be inferred from common file names or ACP.
- Authentication and account selection require provider-specific qualification. SDK availability does not authorize subscription token intermediation. Automatic quota evasion is outside this plan; manual profile support is not equivalent to original F5.
- A local verifier cannot establish universal test correctness. Its enforceable policy and supported project types must be stated precisely, with explicit unsupported outcomes.

## What release sequence fits October 16 through November 30 at 30-40 hours per week?

### Takeaway

Use five public application releases, beginning with an integrated alpha on October 30, with a two-week use experiment ending November 13. Keep approximately 20% of all capacity for verification, required code/security reviews, fixes, packaging, and release documentation. The first month ends November 15; November 16-30 is a conditional expansion and stabilization window.

### Cited Findings

- The owner confirmed one full-time builder using AI coding agents, approximately 30-40 hours weekly, macOS with Claude Code and Codex first, fast releases, and a conditional November-end target for most original feature areas. These are owner planning inputs, not measured team throughput. [Current decision record](../../docs/agent-decisions.md).
- The original document distinguishes canonical history or handoff from native runtime state, identifies configuration and profile clobbering incidents, and records resource conflicts between parallel worktrees. Those are reasons to budget integration and recovery work rather than counting feature names. [Original research, sections 5.2-5.7 and 9](../../docs/Meta-Harness%20%E2%80%94%20Decisions%20Features%20%20Research%20Data.md).
- Official integration and isolation documentation supplies reusable mechanisms, not estimated implementation effort. The following schedule is therefore an engineering planning inference that must be recalibrated after the first qualification and alpha. [Codex app-server](https://developers.openai.com/codex/app-server/), [Tauri security model](https://v2.tauri.app/security/), [Docker Sandbox isolation](https://docs.docker.com/ai/sandboxes/security/isolation/).

### Inferences

October 16-November 30 contains 32 weekdays before holidays or time off. At 6-8 hours per working day, the upper planning capacity is 192-256 gross hours, with approximately 154-205 hours left for feature implementation after a 20% reserve. The 35-hour midpoint is 224 gross hours, approximately 179 feature hours and 45 reserve hours. Thanksgiving or other time off reduces those totals. AI parallelism does not multiply the owner's available review, integration, product decision, or manual qualification time.

Through November 15 there are 21 weekdays: 126-168 gross hours and approximately 101-134 feature hours. The remaining eleven weekdays contribute 66-88 gross hours and approximately 53-70 feature hours. This distinguishes a one-month plan from the full deadline.

| Release and target | Gross capacity in this interval | Feature budget after 20% reserve | Integrated result and release gate |
|---|---:|---:|---|
| v1, October 30 | 11 working days, 66-88 h | 53-70 h | A macOS application creates a project; hosts native Claude and Codex with their permitted login flow; presents supported global/project memory, skills, rules and configuration; routes explicit project-scoped messages; preserves project history; runs basic independent code and test-integrity checks with a protected policy. A real broken implementation plus always-pass tests is rejected. Native account/profile selection is included only where the qualification proves separation; concurrent multi-account behavior is not assumed. |
| v2, November 6 | 5 days, 30-40 h | 24-32 h | Use the same app on daily work. Complete profile isolation and simultaneous account-session checks; make shared state, peer messages, worktree/session recovery and supported configuration reliable. Add project usage attribution with source coverage and unknowns visible. Primary gate: no routine editing of hidden files or switching between external tools to coordinate the supported workflow. |
| v3, November 13 | 5 days, 30-40 h | 24-32 h | Verification beta: stronger integrity detection, source/policy binding, one supported language/toolchain with real unit, integration, whole-flow E2E, smoke and scenario paths where applicable. Budgeted mutation or known-bad checks target changed behavior; findings appear in the project evidence board. Complete the two-week integrated-use go/no-go. This is the first-month checkpoint. |
| v4, November 20 | 5 days, 30-40 h | 24-32 h | After a go decision, expand compatible skills/plugins/MCP and project analytics; qualify one additional harness or the native macOS picker, choosing based on measured pilot need and actual effort. Complete a second modest extension only if the quality reserve and core reliability remain intact. Releasing the integrated product is the commitment; each unqualified feature remains visibly partial or deferred. |

The v1 feature budget is tight. A provisional breakdown includes the architecture lane's 22-hour qualification budget, followed by 8-12 hours to productize the project shell and shared state, 6-10 for native session/profile integration, 2-4 for peer communication, and 10-18 for the minimum protected verifier and negative controls. That totals 48-66 implementation hours before the separate reserve. The qualification work is included, not an additional 22 hours, and its working artifacts must be retained. Reuse must produce a runnable result during the spike. These are planning ranges, not measured estimates; the upper end does not fit the 30-hour/week case without changing dates or obtaining qualified reuse.

The October 21-22 foundation gate should demonstrate, inside an initial application project, both native harnesses consuming one supported project context, one scoped message, and an independently enforced negative control. It must also establish a permitted authentication path, inspect the actual reused component licenses and required notices, and show that a coding process cannot write policy or trusted evidence. If it fails, move public v1 to November 6 or November 13. Do not substitute a terminal recipe or an unprotected test runner to preserve October 30.

Use October 30-November 13 as the two-week application experiment. The following thresholds are proposed product decision rules, not statistical validation:

1. Complete at least ten non-demo project tasks, including tasks requiring both harnesses and independent verification; include at least two external users if available. Record lack of external users as a demand gap, not a passed adoption test.
2. Compare against the owner's existing separate-tool workflow on similar tasks. Target at least 25% less manual coordination time or a comparably material reduction in coordination actions, without a worse completion or defect outcome. Measure time spent correcting context/configuration, account mistakes, switching tools, preparing handoffs, and reconstructing test evidence.
3. At least eight of ten supported workflows complete in the app without manual context/configuration repair outside it. No lost work, cross-project memory leak, wrong-account inference, or unauthorized verifier modification is acceptable.
4. Every supported negative control fails for its intended reason: known-bad behavior, always-pass tests, forbidden policy edits, forged/stale results, and out-of-scope writes. Tests that cannot be run or cannot establish the boundary remain unsupported or blocked.
5. The owner prefers the app for daily work for seven of the ten working days and requests to keep using it. External pilot feedback must explain an integration advantage over a serious existing application, not just over terminal tabs.

Continue after November 13 when the integrated workflow is preferred, reliability is acceptable, and the trust boundary is demonstrated. Rework the application if users need it but keep leaving it to coordinate core work. Stop broad feature expansion if there is no material integration benefit or if an existing application satisfies the same workflow with a small extension. A failed experiment rejects the current implementation or thesis; it does not establish that all integrated agent software is a bad idea.

The critical path is native integration and account semantics, then shared-state and message boundaries, then protected verification, then repeated real workflows and distribution. UI polish, another dashboard, and a third harness are not substitutes for those dependencies.

Capacity failure choices must preserve the core. If the plan overruns, first move an additional harness, native picker, deep analytics, automatic routing, and remote sync. Reduce supported project languages before weakening verification. Move a release date before spending the 20% reserve or dropping required reviews. Do not remove shared project state, direct communication, account separation, or the independent verifier and still label v1 the integrated product.

### Gaps

- The mandatory review tools, Daybreak model/authentication, DeepSec evidence workspace, signing and distribution prerequisites, and external pilot access have not been qualified. They can consume or exceed the reserve and are real schedule dependencies.
- Thirty-hour and forty-hour weeks are materially different: the six-week feature-capacity difference is approximately 51 hours. The schedule needs a weekly reforecast using actual remaining effort.
- Two weeks and ten tasks can guide a personal open-source build decision; they cannot establish population-level demand, long-term security, or superiority on every task.
- The public alpha date depends on clean-machine install and live native-harness checks. A working development checkout alone is not a released application.

## Which original F1-F15 requirements can honestly be in the November beta?

### Takeaway

A credible November beta can make a majority of feature areas useful within declared support boundaries. It cannot honestly promise that most of the fifteen requirements are fully delivered under their original universal semantics. In particular, automatic quota rotation, live preservation of every child process, universal plugin parity, and instant machine/cloud migration remain separate unresolved requirements.

### Cited Findings

- The original F1-F15 definitions are the coverage authority. Their phrases include any harness, without losing history, automatic account switching, subagents and background processes, everything sandboxed, and accounts following across machines. The current owner clarification adds code correctness to independent test-integrity verification rather than replacing it. [Feature list and current decisions](../../docs/Meta-Harness%20%E2%80%94%20Decisions%20Features%20%20Research%20Data.md), [scope correction](../../docs/agent-decisions.md).
- ACP's session/MCP surface and Tauri's UI-to-core boundary are narrower than universal native feature compatibility and workload isolation. Feature completion must follow actual semantics and enforcement, not the presence of an adapter or button. [ACP session source](https://github.com/agentclientprotocol/agent-client-protocol/blob/main/docs/protocol/v2/session-setup.mdx), [Tauri trust boundaries](https://v2.tauri.app/security/).

### Inferences

Each row below retains the original intent. Bounded means the stated behavior works for the published support matrix; partial means core original semantics remain missing. None of these targets is currently implemented or qualified.

| Feature | Initial integrated path | November 30 boundary and honest status |
|---|---|---|

The build recommendation is therefore conditional yes to the integrated application, with protected independent verification as a central feature from the first release. Its November promise should be a useful, coherent macOS beta with transparent support boundaries. A promise of all universal semantics by November 30 is unsupported at the confirmed capacity.

For a practical first release story, demonstrate three observable advantages in one project: Claude and Codex share one approved decision/configuration context, communicate without manual copying, and cannot make their own tests authoritative by weakening the verifier. If that experience is better than the owner's current separate setup and serious existing apps, expand. If it is merely more panes around the same manual coordination, redesign before adding feature count.

### Gaps

- No trustworthy count of fully completed original features can be assigned before a supported matrix and acceptance checks exist. Feature-area coverage must not be reported as full feature completion.
- The choice between the third harness and the native picker is still unresolved. The November experiment should decide it using observed demand and remaining hours.
- Original F5, F6 and F10 have substantial policy or runtime constraints that a faster coding agent cannot remove. Dates for their full semantics require new evidence and a revised scope/capacity decision.
