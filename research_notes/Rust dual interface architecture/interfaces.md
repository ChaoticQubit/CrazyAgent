# Rust desktop and terminal interfaces for CrazyAgent

Research date: October 16, 2026. This lane inspected primary documentation and repository sources. It did not install, compile, execute, benchmark or qualify any framework, repository, harness or platform. Repository `main` branches are moving evidence, not selected production dependencies. Pin a reviewed revision during qualification.

## Which interface frameworks fit the integrated product?

### Takeaway

Recommend a Rust engine used by a Ratatui/Crossterm TUI and a Tauri 2 desktop client, with xterm.js for any desktop terminal view. This is the strongest starting hypothesis for the owner's requirements, not proof that Tauri is universally best. Prefer reusable libraries and selected donor modules; retain Vibe Kanban as a serious timeboxed full-foundation comparison, with the sunset correction below governing its assessment. Both clients must operate the same projects, identities, sessions and verification results.

Tauri core should own system-facing behavior while its webview renders the interface. Its own documentation advises keeping secrets out of the frontend and placing business-sensitive state in the core. [Tauri process model](https://tauri.app/concept/process-model/)

Capabilities limit what windows or webviews can invoke, but are not an operating-system sandbox for child coding processes. Avoid broad filesystem or shell capabilities when a narrow Rust command can validate project/session identity. A protected verification authority requires additional enforcement outside the coder's write authority. [Tauri capabilities](https://tauri.app/security/capabilities/), [security model](https://tauri.app/security/)

The desktop and TUI need equivalent product outcomes, not identical pixel/cell layouts. Desktop can present richer diffs and forms; terminal can use keyboard-focused views. The shared engine should define project IDs, events, errors, session authority and verification state, so neither interface invents a second product model. This is an architectural inference from the requirements, not a framework guarantee.

### Inferences

1. Use Rust for process ownership, adapters, configuration resolution, state changes, messaging and evidence. A web UI in a Tauri webview does not conflict with Rust as the main engine. Rewriting the entire GUI in Rust would not itself provide better isolation or integration correctness.
2. Start with the owner's Tauri preference because its Rust core and web terminal reuse align well. Keep Electron as an evidence-driven fallback if a complete compatible foundation qualifies faster. Do not choose it only because an unrelated app happens to use it.
3. Choose the simplest existing frontend framework that works in the selected foundation. A thin React/TypeScript UI is a practical recommendation if Vibe Kanban modules or components are retained; replacing it with Rust/WASM just to eliminate TypeScript would create migration work. This is not a confirmed stack decision.
4. Treat native menus, keyboard conventions, IME, screen-reader navigation, focus indication and high-DPI scaling as acceptance criteria. A webview window is not automatically a native-quality user experience.

### Gaps

No product prototype, idle-memory measurement, startup comparison, terminal-throughput benchmark, accessibility test or three-platform qualification exists. Avoid numeric speed, RAM or binary-size claims. Tauri's runtime architecture supports a smaller bundled browser footprint than Electron, but model latency, child processes, terminal buffers and I/O may dominate actual resource use. No source establishes a universally best framework for this exact product.

## Which existing code and terminal components should be reused?

### Takeaway

Compare a pinned Vibe Kanban foundation with extracting a few components into a thin Rust engine, but do not assume a supported upstream product: its company shut down and its project routes were sunset. For the primary TUI, use Ratatui to control the application and qualify focused native terminal attachment before committing to multiple embedded emulator panes. Do not accidentally turn CrazyAgent into a new terminal-emulator project.

### Final verification correction: Vibe Kanban maintenance and exact revisions

On April 10, 2026, founder Louis Knight-Webb announced that bloop, the company behind Vibe Kanban, was shutting down. The official post states that the project would continue as open source and community maintained, that remote services would remain for 30 days, and that remote kanban issues, comments, projects and organisations would be removed. Local workspaces explicitly continue to function. This is a company shutdown plus a proposed community-maintained future, not an ordinary cloud retirement with unchanged company support. [Official shutdown announcement](https://www.vibekanban.com/blog/shutdown)

The current official release page still marks `v0.1.44-20260424091429` as latest, released April 24, 2026 at commit `4deb7eca8f381f7cbc1f9d15515a9ab8f8009053`. Its release notes explicitly describe sunsetting project routes to an export-only page. This is directly relevant because CrazyAgent requires usable project creation and management. A full fork must qualify or replace that model rather than assume the original board/project experience remains available. [Official release](https://github.com/BloopAI/vibe-kanban/releases/tag/v0.1.44-20260424091429), [release commit patch](https://github.com/BloopAI/vibe-kanban/commit/4deb7ec.patch)

As checked October 16, 2026, GitHub's `commit/main` resolves to `d5cbb5380fa0b32e98ef9b8d987f63decce4be3a`, a TanStack router API fix whose patch has author date September 19, 2026. Therefore a blanket claim that no upstream commits exist after April is incorrect. This evidence does not establish ongoing maintenance capacity, a new stable release or current compatibility with every native harness. Manifest versions such as `0.1.45` on main must not be presented as a published release. [Current main commit](https://github.com/BloopAI/vibe-kanban/commit/d5cbb5380fa0b32e98ef9b8d987f63decce4be3a), [dated patch](https://github.com/BloopAI/vibe-kanban/commit/d5cbb53.patch)

The June 2, 2026 maintainer discussion asks whether and how to reorganise a community edition and who would contribute maintenance time. The key TUI distinction is rendering a dashboard versus hosting another full-screen interactive terminal. Ratatui draws cells; a VT parser reconstructs child screen state; portable-pty transports bytes. Existing AoE code has separate handling for terminal raw mode, alternate screens, bracketed paste, mouse capture, enhanced keyboard protocols and cleanup after error paths. [Ratatui](https://github.com/ratatui/ratatui), [portable-pty API](https://docs.rs/portable-pty/latest/portable_pty/), [AoE terminal lifecycle](https://raw.githubusercontent.com/agent-of-empires/agent-of-empires/main/src/tui/mod.rs)

Bundle trusted assets, isolate terminal presentation from arbitrary Markdown/HTML, avoid `innerHTML`, and authenticate the transport. A local desktop window does not remove this issue. [xterm.js security guide](https://xtermjs.org/docs/guides/security/)

### Inferences

1. Fastest credible reuse route: use upstream libraries and selected donor code by default, while giving the frozen Vibe Kanban revision a four-hour foundation comparison if a full fork appears promising. It aligns with Rust plus Tauri, but a fork only wins if the sunset project model, local state, native authentication and server lifecycle can be adapted with bounded changes and the owner accepts maintenance responsibility. A fork that needs simultaneous trust-boundary, session model and lifecycle rewrites is not a shortcut. Evidence here is source inspection, not a successful build.
2. Compare three choices concretely: extend the whole Vibe Kanban local spine; extract small coherent process/worktree/adapter pieces with their dependencies; build a thin Rust engine using upstream terminal/protocol libraries and donor patterns. Prefer the smallest complete route that passes the same integrated acceptance flow. Do not copy the whole server merely to obtain one executor.
3. A focused full-screen attach view is a valid v1 alternative to side-by-side embedded TUI panes if accepted during grilling. The dashboard suspends its drawing/input loop, routes the selected session to the physical terminal and uses one documented escape prefix to return. Session lifecycle remains engine-owned, not tied to leaving the view. This reduces layout/composition work, while preserving one application.
4. Full-screen passthrough does not eliminate terminal-state work. Detach/reattach must restore raw mode, cursor, mouse, alternate-screen and keyboard modes; handle output while detached; and redraw the active screen reliably. Replaying an arbitrarily truncated byte log can start inside an escape sequence or lose mode state. Need a qualified multiplexer, coherent VT snapshot/replay, or a documented native redraw mechanism. Do not promise persistence and correct reattachment from plain stdio inheritance alone.
5. A per-platform session backend can use tmux on qualified macOS/Unix while a Windows ConPTY backend matures, but this must be an explicit compatibility boundary. tmux/Zellij prior art is valuable; neither should silently become a universal native Windows prerequisite. Native Windows, WSL and SSH-to-Unix are separate support claims.

### Gaps

No donor has been built or tested here. No reviewed dependency closure or license inventory exists. Vibe Kanban's exact cloud-independent startup, optional telemetry behavior, frontend reuse, account isolation and protected verifier integration need a frozen-revision check. Donor permission flags and local APIs need explicit review. Structured executor support is not identical to hosting an unmodified interactive CLI with its native auth and approval UI. No claim is made that a source fork or extraction can be completed in the research timebox.

## What must be qualified before committing to dates and platform support?

### Takeaway

Keep both required clients, but re-estimate the October 30 milestone after a timeboxed dual-interface qualification. The previously approved 22-hour critical-path estimate did not establish an implemented TUI plus desktop product. Make the added work visible; do not treat shared Rust business logic as free interface parity.

### Cited Findings

Tauri development prerequisites differ: macOS uses Xcode tooling; Windows needs Microsoft C++ build tools and WebView2; Linux needs distribution-specific WebKitGTK/system libraries. These are framework prerequisites, not proof a harness is supported on that OS. [Tauri prerequisites](https://tauri.app/start/prerequisites/)

Tauri has cross-platform distribution tooling and an updater plugin with required cryptographic update signatures. macOS signing/notarization and Windows packaging/signing are additional release tasks. A TUI binary can have a separate archive/package distribution path. [Tauri distribution](https://tauri.app/distribute/), [updater](https://tauri.app/plugin/updater/), [macOS signing](https://tauri.app/distribute/sign/macos/), [Windows signing](https://tauri.app/distribute/sign/windows/)

For high-volume native-to-webview events, Tauri documents channels as the recommended streaming mechanism rather than treating its ordinary event system as a high-throughput queue. This supports a bounded stream design but does not benchmark terminal workloads. [Calling the frontend](https://tauri.app/develop/calling-frontend/)

The most valuable next grilling questions are ordered dependencies, not framework trivia: whether agents survive closing both UIs; whether both clients can attach simultaneously; whether only one client can own terminal input; whether full-screen native terminal attachment is acceptable in the primary TUI; and what the minimum complete desktop journey must include. These answers determine process boundaries and costs before selecting individual crates.

### Gaps

No source or experiment currently establishes that both complete clients and all prior v1 acceptance criteria fit October 30 in 53-70 feature hours. Existing libraries reduce implementation work but do not remove native auth, terminal protocol, cross-client state, OS isolation or packaging tests. No Windows/Linux hardware access, signer setup or CI readiness was verified in this lane. Final dates should follow the accepted interface semantics and the qualification results.
